# HubSpot V4 Records Reference

> Surface: `Schema = HubSpotV4`. A lean record-focused view of the CRM. Load this reference when the live connection's `getSchemas` returns **`HubSpotV4`**. See the base [SKILL.md](../SKILL.md) for surface identification.
>
> This surface (~62 tables) is deliberately narrower than the V3 catalog: object tables, their association tables, property-history views, and email subscription management. It carries **no** property or pipeline definition tables, no owner or user lookups, no lists, no marketing or CMS content, and no file operations. Its one capability V3 lacks is email subscription management.

## Schema

The schema name is `HubSpotV4`. The three-part name is `[Catalog].[HubSpotV4].[Table]`:

```sql
SELECT [Id], [Deal Name], [Amount], [Deal Stage] FROM [YourConnection].[HubSpotV4].[Deals] LIMIT 10
```

Replace `[YourConnection]` with your actual HubSpot connection name from `getCatalogs`.

## Know when this is the wrong surface (read this first)

Because V4 has no lookup tables, several common requests cannot be answered fully here. Recognize them early rather than approximating with raw ids:

| Request | On V4 | What to do |
|---|---|---|
| Results by a person's name (owner, rep, assignee) | Owner columns return numeric ids; there is no `Owners` table | Say a `HubSpotV3` connection is needed, or report by owner id if the user accepts it |
| A portal's custom pipeline stage labels | Deal stages return HubSpot's internal names, not the portal's labels | Group on the internal name, or use `HubSpotV3` for labels |
| A ticket's status or pipeline by name | `[Ticket status]` and `[Pipeline]` return **numeric ids**, and there is no `TicketPipelineStages` table here | Requires a `HubSpotV3` connection |
| Creating a new record | A raw `INSERT` does not work — the key is server-assigned | Use the object's dedicated create Source Tool; see **Write Operations** |
| Discovering a custom property's label | No `*Properties` tables | `getColumns` is the only discovery path here |
| List membership / segmentation | No `Lists` or `ListMemberships` | Requires a `HubSpotV3` connection |
| Marketing assets, campaigns, forms, CMS content | Not present | Requires a `HubSpotV3` connection |
| Custom object type metadata | No `CustomObjects` tables | Requires a `HubSpotV3` connection |
| File upload or retrieval | No file tables or procedures | Requires `HubSpotV3`, or legacy for upload |

## Query Process

1. **Identify the object.** Object tables are plural — `Contacts`, `Companies`, `Deals`, `Tickets`, `Leads`, `Quotes`, `Invoices`, `Orders`, `Products`, `Lineitems`.
2. **Confirm the columns with `getColumns`.** There are no property-definition tables on this surface, so this is the only way to discover a portal-specific property.
3. **Work with stage and owner values directly.** No lookup tables exist. A deal's `[Deal Stage]` holds HubSpot's internal stage name (`appointmentscheduled`, `closedwon`), which is readable enough to filter and group on. A ticket's `[Ticket status]` and `[Pipeline]`, by contrast, hold **numeric ids** with nothing on this surface to resolve them against. Owner columns likewise hold numeric ids.
4. **Go through association tables for relationships.** Never expect a foreign key on the object itself.

## Data Model

### Key Tables

**Core CRM objects** — **Contacts**, **Companies**, **Deals**, **Tickets**, **Leads**.

**Engagement (activity) objects** — exposed with an `Engagements` prefix: **EngagementsCalls**, **EngagementsEmails**, **EngagementsMeetings**, **EngagementsNotes**, **EngagementsTasks**. Also **Communications** and **PostalMails**.

**Commerce objects** — **Quotes**, **Invoices**, **Orders**, **Subscriptions**, **Products**, **Lineitems**.

**Other CRM objects** — **Appointments**, **Courses**, **Listings**, **Services**, **Feedbacksubmissions**, **Goals**.

**Property history views** — **ContactPropertiesHistory**, **CompanyPropertiesHistory**, **DealPropertiesHistory**, **TicketPropertiesHistory**, **LeadPropertiesHistory**, **OrderPropertiesHistory**. Historical values of a property over time. The record key is named after the object — `[DealId]`, `[ContactId]` — **not** `ObjectId`, and `ContactPropertiesHistory` adds `[ContactEmail]` and `[ContactPhoneNumber]`. On this surface these views **require a `[PropertyName]` filter**; supplying only the record id errors.

**Email subscription management** — the capability this surface has that V3 does not:
- **SubscriptionTypes** — the portal's subscription types, with `[Name]`, `[Purpose]`, `[CommunicationMethod]`, `[IsActive]`, `[IsDefault]`, `[IsInternal]`
- **SubscriptionPreferences** — a contact's per-type subscription status. **Requires an `[Email]` filter**; without one the query errors.

### The Association Model

Relationships live in junction tables. Which tables exist depends on the **`ExpandAssociations`** connection property, and only one shape is active on a given connection. Run one filtered `getTables` call first, using the object's singular root token so it matches either shape:

```json
{"catalogName": "YourConnection", "schemaName": "HubSpotV4", "tableName": "%Deal%Associations%"}
```

**Shape A — per-object tables (`ExpandAssociations=false`, the default).** One table per object, named with the object's **singular** stem: `ContactAssociations`, `CompanyAssociations`, `DealAssociations`, `TicketAssociations`, `LeadAssociations`, `QuoteAssociations`, `InvoiceAssociations`, `OrderAssociations`, `ProductAssociations`, `LineitemAssociations`, `SubscriptionAssociations`, `AppointmentAssociations`, `CourseAssociations`, `ListingAssociations`, `ServiceAssociations`, `FeedbackSubmissionAssociations`, `PostalmailAssociations`, `CallAssociations`, `EmailAssociations`, `MeetingAssociations`, `NoteAssociations`, `TaskAssociations`, `CommunicationAssociations`. Note the inconsistent internal capitalization (`FeedbackSubmissionAssociations` with a capital S, `PostalmailAssociations` with a lowercase m).

Columns are `[Id]` (the source object's id), `[AssociationId]` (the related object's id), and `[Type]` (what the related object is). `[Type]` values are TitleCase singular, with an underscore where the object name is two words — `Contact`, `Company`, `Deal`, `Ticket`, `Quote`, `Call`, `Line_item`.

**Shape B — pairwise tables (`ExpandAssociations=true`).** One table per ordered pair, named `<From>To<Target>Associations` using the **plural** table tokens. The set present depends on which associations the portal defines; commonly available pairs:

| From object | Target objects |
|---|---|
| Appointments | Companies, Contacts, Deals, Tickets |
| Companies | Calls, Contacts, Deals, Emails, Meetings, Notes, Quotes, Tasks, Tickets |
| Contacts | Calls, Deals, Emails, Meetings, Notes, Quotes, Tasks, Tickets |
| Courses | Companies, Contacts, Deals, Tickets |
| Deals | Calls, Emails, Lineitems, Meetings, Notes, Quotes, Tasks, Tickets |
| Feedbacksubmissions | Contacts, Tickets |
| Invoices | Lineitems |
| Leads | Calls, Communications, Companies, Contacts, Emails, Meetings, Tasks |
| Lineitems | Quotes |
| Listings | Companies, Contacts, Deals, Tickets |
| Orders | Companies, Contacts, Deals, Lineitems, Quotes, Tasks, Tickets |
| Products | Deals |
| Services | Companies, Contacts, Deals, Tickets |
| Subscriptions | Companies, Contacts, Deals, Invoices, Quotes, Tickets |

Each pair is materialized in one direction only — if `CompaniesToDealsAssociations` exists, `DealsToCompaniesAssociations` generally does not. Some objects appear only as a target: there are `CompaniesToTicketsAssociations` and `ContactsToTicketsAssociations`, but no `TicketsTo*Associations` tables. Portals with custom objects get additional pairs.

Columns are `<From>Id` and `<Target>Id` — the full plural token plus `Id` (`CompaniesId`, `DealsId`, `LineitemsId`) — plus `[TypeId]`, `[Category]`, and `[TypeLabel]`. For engagement objects the token keeps the prefix: `ContactsToCallsAssociations` has `ContactsId` and `EngagementsCallsId`. **There is no `[Type]` column in this shape** — that belongs to Shape A only.

**AssociationsLabels** is a view (not a stored procedure) listing the association types defined between a pair of object types. It requires both filters, and object types are lowercase plural. Columns are `[TypeId]`, `[Category]`, `[Label]`, `[FromObjectType]`, `[ToObjectType]` — the id lives in **`[TypeId]`**, not `[Id]`. `[Category]` distinguishes `HUBSPOT_DEFINED` types from portal-defined ones. Note the name differs from V3, which calls this view `AssociationsTypes` and names the same value `[Id]`. `[TypeId]` is also the value the legacy surface's `CrmAssociations.[DefinitionId]` expects.

### Key Relationships

- Object → object: always through an association table (see above).
- `SubscriptionPreferences.[SubscriptionTypeId]` → `SubscriptionTypes.[Id]`.
- `*PropertiesHistory.[ObjectId]` → the object's `[Id]`.
- Stage and owner columns have **no** lookup table on this surface.

## Important Columns

Every CRM object table carries `[Id]` (BIGINT primary key — the HubSpot record id, and the key every association table joins on), `[CreatedAt]`, `[UpdatedAt]`, `[Archived]`, and `[ItemURL]` (a deep link to the record in the HubSpot UI).

> Object tables also expose a separate `Record ID` **property** column. `[Id]` is the primary key — use it for joins and filters, not `[Record ID]`.

### Contacts
- `Email`, `First Name`, `Last Name` — identity, in separate columns
- `Mobile Phone Number`, `Job Title`, `City`, `Industry`
- `Company Name` — the contact's company name, set independently of the associated company record's own name
- `Lifecycle Stage` — qualification toward sales readiness (lowercase values, e.g. `lead`, `opportunity`)
- `Lead Status` — sales, prospecting, or outreach status
- `Contact owner` — owner id, with no table to resolve it
- `Create Date`, `Last Activity Date`, `Last Contacted`
- `Number of Associated Deals` — rollup maintained by HubSpot

### Companies
- `Company name` — the organization's name (lowercase `n`)
- `Company Domain Name`, `Industry`, `Type`
- `City`, `State/Region`, `Country/Region`
- `Annual Revenue`, `Number of Employees`
- `Lifecycle Stage`, `Company owner`
- `Create Date`, `Last Activity Date`
- `Number of open deals`, `Total open deal value` — rollups maintained by HubSpot
- `Parent Company`

### Deals
- `Deal Name`, `Amount`, `Deal Type`, `Priority`
- `Deal Stage` — HubSpot's internal stage name (e.g. `appointmentscheduled`, `qualifiedtobuy`, `closedwon`)
- `Pipeline` — the pipeline's internal name (e.g. `default`)
- `Close Date`, `Create Date`
- `Deal owner` — owner id, with no table to resolve it
- `Is Deal Closed?` — true when won or lost (note the trailing question mark)
- `Is Open (numeric)` — 1 when neither closed won nor closed lost, 0 otherwise. Read-only, and often the most direct filter for open deals
- `Is Closed Won`, `Is closed lost` — outcome flags (note the lowercase `c` and `l` on the latter)
- `Deal probability`, `Forecast amount`
- `Closed Won Reason`, `Closed Lost Reason`
- `Number of Associated Contacts`, `Number of Associated Line Items`

### Tickets
- `Ticket name` — short summary
- `Ticket status` — the pipeline stage **id** (numeric), with no lookup table on this surface
- `Pipeline` — the pipeline **id** (numeric)
- `Priority` (e.g. `HIGH`, `LOW`), `Category`, `Source` (e.g. `CHAT`)
- `Create date`, `Close date` — note the lowercase `d`
- `Closed` — whether the ticket is considered closed
- `Ticket owner`, `Last activity date`, `Resolution`, `Time to close`

### SubscriptionPreferences
- `Email` — the contact's email address; **required as a filter**
- `SubscriptionTypeId` — the subscription type; resolve through `SubscriptionTypes`
- `Channel` — the communication channel (e.g. `EMAIL`)
- `Status` — `SUBSCRIBED`, `UNSUBSCRIBED`, or `NOT_SPECIFIED`
- `Source` — how the preference was set
- `LegalBasis`, `LegalBasisExplanation` — consent basis
- `Timestamp` — when the preference was last set

## Common Query Patterns

### Open deals, largest first
```sql
SELECT [Id], [Deal Name], [Amount], [Deal Stage], [Close Date]
FROM [YourConnection].[HubSpotV4].[Deals]
WHERE [Is Deal Closed?] = 0
ORDER BY [Amount] DESC
LIMIT 25
```

### Pipeline snapshot — open deals per stage and total value
With no pipeline-stages table to join, group on `[Deal Stage]` directly. Values are HubSpot's internal stage names.
```sql
SELECT [Deal Stage], COUNT(*) AS [Deals], SUM([Amount]) AS [Value]
FROM [YourConnection].[HubSpotV4].[Deals]
WHERE [Is Deal Closed?] = 0
GROUP BY [Deal Stage]
ORDER BY [Value] DESC
```

### Closed-won revenue by month, current year
```sql
SELECT MONTH([Close Date]) AS [MonthNum], SUM([Amount]) AS [Revenue]
FROM [YourConnection].[HubSpotV4].[Deals]
WHERE [Is Closed Won] = 1 AND YEAR([Close Date]) = YEAR(GETDATE())
GROUP BY MONTH([Close Date])
ORDER BY [MonthNum]
```

### Deal counts and wins by owner id
There is no `Owners` table on this surface, so results group by owner id rather than name.
```sql
SELECT [Deal owner],
       COUNT(*) AS [Total Deals],
       SUM(CASE WHEN [Is Closed Won] = 1 THEN 1 ELSE 0 END) AS [Closed Won]
FROM [YourConnection].[HubSpotV4].[Deals]
GROUP BY [Deal owner]
ORDER BY [Closed Won] DESC
LIMIT 20
```

### Contacts by lifecycle stage
```sql
SELECT [Id], [Email], [First Name], [Last Name], [Lifecycle Stage], [Create Date]
FROM [YourConnection].[HubSpotV4].[Contacts]
WHERE [Lifecycle Stage] = 'opportunity'
ORDER BY [Create Date] DESC
LIMIT 50
```

### Open tickets by status and priority
```sql
SELECT [Id], [Ticket name] AS [Subject], [Ticket status], [Priority], [Create date]
FROM [YourConnection].[HubSpotV4].[Tickets]
WHERE [Closed] = 0
ORDER BY [Create date] DESC
LIMIT 25
```

### Recently created deals
```sql
SELECT [Id], [Deal Name], [Amount], [Create Date]
FROM [YourConnection].[HubSpotV4].[Deals]
WHERE [Create Date] >= DATEADD(month, -3, GETDATE())
ORDER BY [Create Date] DESC
LIMIT 50
```

### A contact's email subscription status
`SubscriptionPreferences` requires an `[Email]` filter.
```sql
SELECT [Email], [SubscriptionTypeId], [Channel], [Status], [Source], [Timestamp]
FROM [YourConnection].[HubSpotV4].[SubscriptionPreferences]
WHERE [Email] = 'someone@example.com'
```

The portal's subscription types, for resolving `[SubscriptionTypeId]`:
```sql
SELECT [Id], [Name], [Purpose], [CommunicationMethod], [IsActive], [IsDefault], [IsInternal]
FROM [YourConnection].[HubSpotV4].[SubscriptionTypes]
```

### A company's deals, through associations (per-object shape)
```sql
SELECT DISTINCT d.[Id], d.[Deal Name], d.[Amount], d.[Deal Stage]
FROM [YourConnection].[HubSpotV4].[CompanyAssociations] a
INNER JOIN [YourConnection].[HubSpotV4].[Deals] d ON d.[Id] = a.[AssociationId]
WHERE a.[Type] = 'Deal' AND a.[Id] = <company-id>
```

### A company's deals, through associations (pairwise shape)
```sql
SELECT DISTINCT d.[Id], d.[Deal Name], d.[Amount], a.[TypeLabel]
FROM [YourConnection].[HubSpotV4].[CompaniesToDealsAssociations] a
INNER JOIN [YourConnection].[HubSpotV4].[Deals] d ON d.[Id] = a.[DealsId]
```

### What object types a record is associated with
```sql
SELECT [Type], COUNT(*) AS [Rows]
FROM [YourConnection].[HubSpotV4].[DealAssociations]
GROUP BY [Type]
```

### Which association types exist between two objects
```sql
SELECT [TypeId], [Category], [Label], [FromObjectType], [ToObjectType]
FROM [YourConnection].[HubSpotV4].[AssociationsLabels]
WHERE [FromObjectType] = 'deals' AND [ToObjectType] = 'contacts'
```

### How a property changed over time
The record key is `[DealId]` (not `ObjectId`), and a `[PropertyName]` filter is **required** on this surface.
```sql
SELECT [DealId], [PropertyName], [Value], [Timestamp], [SourceType]
FROM [YourConnection].[HubSpotV4].[DealPropertiesHistory]
WHERE [PropertyName] = 'dealstage' AND [DealId] = <deal-id>
ORDER BY [Timestamp] DESC
```

This is also the way to reconstruct a deal's stage progression on V4, which has no equivalent of the legacy surface's `DealStages` table.

## Stored Procedures

This surface's procedures are focused on email subscription management:

- **EnableSubscriptionPreferences** — subscribes a contact to a subscription type. HubSpot also enables the account's other subscription types for that contact with a default status of `NOT_SPECIFIED`.
- **UpdateSubscriptionPreferences** — changes a contact's subscription status for a type
- **AddOptedOutContacts** — unsubscribes a contact from all subscription preferences
- **GetAccountDetails** — account type, time zone, currencies, data hosting location

Custom object and property definition, permanent contact deletion, and file management are **not** available here — those live on `HubSpotV3`.

## Write Operations

**`UPDATE` is the supported write path on the object tables**, subject to the connection's permissions. Target the record by `[Id]`:

```sql
UPDATE [YourConnection].[HubSpotV4].[Deals]
SET [Amount] = 12000, [Deal Stage] = 'qualifiedtobuy'
WHERE [Id] = <deal-id>
```

When writing a stage, use HubSpot's internal stage name. Since this surface has no stages table, sample existing values with `SELECT DISTINCT [Deal Stage]` to see what the portal uses.

### Creating records

A raw `INSERT` against the object tables does **not** work. HubSpot assigns each record's primary key server-side and exposes `[Id]` as read-only, while the insert path requires a value for every non-nullable column that has no default and does not skip the read-only key — so the statement is rejected before the driver sees it.

**Creation is still supported**, through the connection's dedicated create tool for the object, which reaches the driver by a path that lets HubSpot generate the key. Use it in preference to any `INSERT`.

- **Never supply `[Id]`** on a create.
- An error naming the key column as *"neither nullable nor has a default value"* is a property of the insert path, not a missing column. Switch to the create tool rather than retrying variants or inventing a key value.
- **Confirm the create by reading the record back** by the id the tool returns.
- If no create tool is listed in this session, say plainly that creation is unavailable here, and offer to update an existing record or point the user to the HubSpot UI.

### Write access control
A Connect AI connection may also be set to read-only. If an update or stored procedure is refused on permission grounds, direct the user to enable write access in their Connect AI connection settings. That is a different cause from the insert-path behavior above — do not send a user to connection settings over an insert error.

## V4-Specific Conventions

- **No lookup tables.** Owner columns and stage columns cannot be resolved to names or portal labels here. Check the table at the top of this reference before promising a name-based answer.
- **`getColumns` is the only property discovery path.** There are no `*Properties` tables on this surface.
- **Enum values are lowercase**, matching V3 — `[Lifecycle Stage]` is `lead` / `opportunity`. Legacy uses TitleCase.
- **Two kinds of required filter live here.** `SubscriptionPreferences` errors without an `[Email]` filter, and the `*PropertiesHistory` views error without a `[PropertyName]` filter. Supply them rather than removing filters. Note the history views do **not** require `PropertyName` on V3 — this is surface-specific.
- **Property-history key columns are object-named.** `[DealId]`, `[ContactId]` — never `ObjectId`.
- **`UPDATE` works; a raw `INSERT` does not.** Creation goes through the object's dedicated create Source Tool, and the primary key is never supplied. See **Write Operations**.
- **The association-types view is named `AssociationsLabels` here**, not `AssociationsTypes` as on V3, and its id column is `[TypeId]` where V3's is `[Id]`.
- **Picklist values usually require sampling.** With few lookup tables, `SELECT DISTINCT` is more often the only option here than on V3 — use `SubscriptionTypes` and `AssociationsLabels` where they apply.
- **`[Id]` is the primary key, not `[Record ID]`.** Both exist on object tables.

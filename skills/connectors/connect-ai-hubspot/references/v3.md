# HubSpot V3 Catalog Reference

> Surface: `Schema = HubSpotV3`. The full HubSpot catalog. Load this reference when the live connection's `getSchemas` returns **`HubSpotV3`**. See the base [SKILL.md](../SKILL.md) for surface identification.
>
> This is the richest of the three surfaces (~137 tables) and the right default for most work. It is the only surface carrying property and pipeline definition tables, owner and user lookups, list membership, marketing and CMS content, and custom-object metadata.

## Schema

The schema name is `HubSpotV3`. The three-part name is `[Catalog].[HubSpotV3].[Table]`:

```sql
SELECT [Id], [Deal Name], [Amount], [Deal Stage] FROM [YourConnection].[HubSpotV3].[Deals] LIMIT 10
```

Replace `[YourConnection]` with your actual HubSpot connection name from `getCatalogs`.

## Query Process

1. **Identify the object.** Object tables are plural — `Contacts`, `Companies`, `Deals`, `Tickets`, `Leads`, `Quotes`, `Invoices`, `Orders`, `Products`, `Lineitems`.
2. **Confirm the columns.** Labels are portal-specific display names. Use `getColumns` with a `columnName` filter, or query the object's `*Properties` table by `[Label]`.
3. **Resolve ids to labels.** `[Deal Stage]`, `[Ticket status]`, `[Pipeline]`, and every `*owner` column hold ids. Join the matching `*PipelineStages` or `Owners` table when the user wants readable output.
4. **Go through association tables for relationships.** Never expect a foreign key on the object itself.

## Data Model

### Key Tables

**Core CRM objects**
- **Contacts** — people; the most property-rich object in most portals
- **Companies** — organizations, with rollup columns like `[Number of open deals]`
- **Deals** — sales opportunities, with amount, stage, pipeline, and close date
- **Tickets** — service requests, with status, priority, and pipeline
- **Leads** — top-of-funnel lead records

**Engagement (activity) objects** — exposed with an `Engagements` prefix: **EngagementsCalls**, **EngagementsEmails**, **EngagementsMeetings**, **EngagementsNotes**, **EngagementsTasks**. Also **Communications** and **PostalMails**.

**Commerce objects** — **Quotes**, **Invoices**, **Orders**, **Subscriptions**, **Products**, **Lineitems**.

**Other CRM objects** — **Appointments**, **Courses**, **Listings**, **Services**, **Feedbacksubmissions**, **Goals**.

**Users, owners, teams, and roles**
- **Owners** — the assignable record owner. Use this to turn an owner id into a person's name; `[FirstName]` and `[LastName]` are separate columns.
- **UserProvisioning** — user accounts with admin, role, and team attributes. Prefer this for administrative questions.
- **Teams** / **Roles** — team and role definitions.
- **Users** — lower-level user records (working hours, time zone, job title).

**Lists and segmentation** — **Lists** (definitions, with `[ProcessingType]` of `MANUAL` / `DYNAMIC` / `SNAPSHOT`) and **ListMemberships** (which records belong to which list).

**Marketing and content** — **Campaigns**, **MarketingEmails**, **MarketingEvents**, **Forms**, **Workflows**, **PerformanceWorkflows**, **BlogPosts**, **Blogs**, **BlogAuthors**, **BlogTags**, **LandingPages**, **SitePages**, **URLRedirects**, **Domains**, **Files**, **Folders**, **Threads**, **ThreadMessages**, **WebAnalytics**.

**Custom object metadata** — **CustomObjects**, **CustomObjectProperties**, **CustomObjectAssociations**.

### Property, Pipeline, and Metadata Table Families

Each object has companion metadata tables for discovering custom property labels and resolving ids to display names:

| Family | Purpose | Examples |
|---|---|---|
| `*Properties` | Property (column) definitions, including custom ones | `ContactProperties`, `DealProperties`, `TicketProperties`, `LeadProperties`, `LineItemProperties`, `CallProperties`, `NoteProperties`, `OrderProperties`, `QuoteProperties` |
| `*PropertyGroups` | How properties are grouped in the UI | `ContactPropertyGroups`, `DealPropertyGroups`, `TicketPropertyGroups` |
| `*Pipelines` | Pipeline definitions | `DealPipelines`, `TicketPipelines`, `LeadPipelines`, `OrderPipelines` |
| `*PipelineStages` | Stages within a pipeline, carrying the `[Label]` | `DealPipelineStages`, `TicketPipelineStages`, `LeadPipelineStages` |
| `*PropertiesHistory` | Historical values of a property | `ContactPropertiesHistory`, `DealPropertiesHistory`, `TicketPropertiesHistory` |

The prefix is generally the object's singular name, but **capitalization is not consistent across families**. The deal family is `DealProperties` / `DealPipelines` / `DealPipelineStages`, while line items are `LineItemProperties` (capital I) even though the object table is `Lineitems` and its association table is `LineitemAssociations` (lowercase i). Postal mail behaves the same way: `PostalMails`, `PostalMailProperties`, `PostalmailAssociations`. Confirm the exact name with one filtered `getTables` call rather than constructing it.

### The Association Model

Relationships live in junction tables. Which tables exist depends on the **`ExpandAssociations`** connection property, and only one shape is active on a given connection. Run one filtered `getTables` call first, using the object's singular root token so it matches either shape:

```json
{"catalogName": "YourConnection", "schemaName": "HubSpotV3", "tableName": "%Deal%Associations%"}
```

**Shape A — per-object tables (`ExpandAssociations=false`, the default).** One table per object, named with the object's **singular** stem: `ContactAssociations`, `CompanyAssociations`, `DealAssociations`, `TicketAssociations`, `LeadAssociations`, `QuoteAssociations`, `InvoiceAssociations`, `OrderAssociations`, `ProductAssociations`, `LineitemAssociations`, `SubscriptionAssociations`, `AppointmentAssociations`, `CourseAssociations`, `ListingAssociations`, `ServiceAssociations`, `FeedbackSubmissionAssociations`, `PostalmailAssociations`, `CallAssociations`, `EmailAssociations`, `MeetingAssociations`, `NoteAssociations`, `TaskAssociations`, `CommunicationAssociations`. Note the inconsistent internal capitalization (`FeedbackSubmissionAssociations` with a capital S, `PostalmailAssociations` with a lowercase m).

Columns are `[Id]` (the source object's id), `[AssociationId]` (the related object's id), and `[Type]` (what the related object is). `[Type]` values are TitleCase singular, with an underscore where the object name is two words — `Contact`, `Company`, `Deal`, `Ticket`, `Quote`, `Call`, `Line_item`.

**Shape B — pairwise tables (`ExpandAssociations=true`).** One table per ordered pair, named `<From>To<Target>Associations` using the **plural** table tokens — `CompaniesToDealsAssociations`, `ContactsToDealsAssociations`, `DealsToLineitemsAssociations`. Each pair is materialized in one direction only, and some objects appear only as a target: there are `CompaniesToTicketsAssociations` and `ContactsToTicketsAssociations`, but no `TicketsTo*Associations` tables.

Columns are `<From>Id` and `<Target>Id` — the full plural token plus `Id` (`CompaniesId`, `DealsId`, `LineitemsId`) — plus `[TypeId]`, `[Category]`, and `[TypeLabel]`. For engagement objects the token keeps the prefix: `ContactsToCallsAssociations` has `ContactsId` and `EngagementsCallsId`. **There is no `[Type]` column in this shape** — that belongs to Shape A only, and mixing them up is a common failure.

**AssociationsTypes** is a view (not a stored procedure) listing the association types defined between a pair of object types. It requires both filters, and object types are lowercase plural. Columns are `[Id]`, `[Type]`, `[FromObjectType]`, `[ToObjectType]`.

```sql
SELECT [Id], [Type], [FromObjectType], [ToObjectType]
FROM [YourConnection].[HubSpotV3].[AssociationsTypes]
WHERE [FromObjectType] = 'contacts' AND [ToObjectType] = 'companies'
```

An object pair commonly has several types — contacts-to-companies returns `1` (`company`), `279` (`company_unlabeled`), and any portal-defined ones. `[Id]` is also the value the legacy surface's `CrmAssociations.[DefinitionId]` expects. Note that V4's equivalent view is named `AssociationsLabels` and names the same value `[TypeId]`, not `[Id]`.

### Key Relationships

- Object → object: always through an association table (see above).
- `Deals.[Deal Stage]` → `DealPipelineStages.[Id]`, which carries `[Label]`. Same shape for tickets and leads.
- Any `*owner` column → `Owners.[Id]`.
- `UserProvisioning.[PrimaryTeamId]` → `Teams.[Id]`.
- `ListMemberships.[ObjectId]` → the object's `[Id]`, scoped by `[ListId]`. Do not filter on `[ObjectTypeId]` — see the pattern below.

## Important Columns

Every CRM object table carries `[Id]` (BIGINT primary key — the HubSpot record id, and the key every association table joins on), `[CreatedAt]`, `[UpdatedAt]`, `[Archived]`, and `[ItemURL]` (a deep link to the record in the HubSpot UI).

> Object tables also expose a separate `Record ID` **property** column. `[Id]` is the primary key — use it for joins and filters, not `[Record ID]`.

### Contacts
- `Email`, `First Name`, `Last Name` — identity, in separate columns
- `Mobile Phone Number`, `Job Title`, `City`, `Industry`
- `Company Name` — the contact's company name, set independently of the associated company record's own name
- `Lifecycle Stage` — qualification toward sales readiness (lowercase values, e.g. `lead`, `opportunity`)
- `Lead Status` — sales, prospecting, or outreach status
- `Contact owner` — owner id; join `Owners` for a name
- `Create Date`, `Last Activity Date`, `Last Contacted`
- `Number of Associated Deals` — rollup maintained by HubSpot

### Companies
- `Company name` — the organization's name (lowercase `n`)
- `Company Domain Name`, `Industry`, `Type`
- `City`, `State/Region`, `Country/Region`
- `Annual Revenue`, `Number of Employees`
- `Lifecycle Stage`, `Company owner`
- `Create Date`, `Last Activity Date`
- `Number of open deals`, `Total open deal value` — rollups maintained by HubSpot
- `Parent Company`

### Deals
- `Deal Name`, `Amount`, `Deal Type`, `Priority`
- `Deal Stage` — the stage **id**; join `DealPipelineStages` for the label
- `Pipeline` — the pipeline **id**
- `Close Date`, `Create Date`
- `Deal owner` — owner id
- `Is Deal Closed?` — true when won or lost (note the trailing question mark)
- `Is Open (numeric)` — 1 when neither closed won nor closed lost, 0 otherwise. Read-only, and often the most direct filter for open deals
- `Is Closed Won`, `Is closed lost` — outcome flags (note the lowercase `c` and `l` on the latter)
- `Deal probability`, `Forecast amount`
- `Closed Won Reason`, `Closed Lost Reason`
- `Number of Associated Contacts`, `Number of Associated Line Items`

### Tickets
- `Ticket name` — short summary
- `Ticket status` — the pipeline stage **id**; join `TicketPipelineStages` for the label
- `Pipeline` — the pipeline id
- `Priority` (e.g. `HIGH`, `LOW`), `Category`, `Source` (e.g. `CHAT`)
- `Create date`, `Close date` — note the lowercase `d`
- `Closed` — whether the ticket is considered closed
- `Ticket owner`, `Last activity date`, `Resolution`, `Time to close`

### Owners
- `Id` — the owner id that every `*owner` column points at
- `FirstName`, `LastName` — unspaced, unlike the CRM object tables
- `Email`

### ListMemberships
- `ObjectId` — the member record's id
- `ListId` — the list's id; **required as a filter**
- `ObjectTypeId` — the member's object type (`0-1` contacts, `0-2` companies, `0-3` deals). Readable, but **not filterable** — a predicate on it silently returns zero rows
- `MembershipTimestamp` — when the record joined the list

## Common Query Patterns

### Open deals, largest first
```sql
SELECT [Id], [Deal Name], [Amount], [Deal Stage], [Close Date]
FROM [YourConnection].[HubSpotV3].[Deals]
WHERE [Is Deal Closed?] = 0
ORDER BY [Amount] DESC
LIMIT 25
```

### Pipeline snapshot — open deals per stage label and total value
```sql
SELECT s.[Label] AS [Stage], COUNT(*) AS [Open Deals], SUM(d.[Amount]) AS [Total Value]
FROM [YourConnection].[HubSpotV3].[Deals] d
LEFT JOIN [YourConnection].[HubSpotV3].[DealPipelineStages] s ON s.[Id] = d.[Deal Stage]
WHERE d.[Is Deal Closed?] = 0
GROUP BY s.[Label]
ORDER BY [Total Value] DESC
```

### Closed-won revenue by month, current year
```sql
SELECT MONTH([Close Date]) AS [MonthNum], SUM([Amount]) AS [Revenue]
FROM [YourConnection].[HubSpotV3].[Deals]
WHERE [Is Closed Won] = 1 AND YEAR([Close Date]) = YEAR(GETDATE())
GROUP BY MONTH([Close Date])
ORDER BY [MonthNum]
```

### Deal counts and wins by owner name
```sql
SELECT CONCAT(o.[FirstName], ' ', o.[LastName]) AS [Rep],
       COUNT(*) AS [Total Deals],
       SUM(CASE WHEN d.[Is Closed Won] = 1 THEN 1 ELSE 0 END) AS [Closed Won]
FROM [YourConnection].[HubSpotV3].[Deals] d
LEFT JOIN [YourConnection].[HubSpotV3].[Owners] o ON o.[Id] = d.[Deal owner]
GROUP BY o.[Id], o.[FirstName], o.[LastName]
ORDER BY [Closed Won] DESC
LIMIT 20
```

### Contacts by lifecycle stage
```sql
SELECT [Id], [Email], [First Name], [Last Name], [Lifecycle Stage], [Create Date]
FROM [YourConnection].[HubSpotV3].[Contacts]
WHERE [Lifecycle Stage] = 'opportunity'
ORDER BY [Create Date] DESC
LIMIT 50
```

### Open tickets with status label and owner name
```sql
SELECT t.[Id], t.[Ticket name] AS [Subject], s.[Label] AS [Status], t.[Priority],
       CONCAT(o.[FirstName], ' ', o.[LastName]) AS [Rep]
FROM [YourConnection].[HubSpotV3].[Tickets] t
LEFT JOIN [YourConnection].[HubSpotV3].[TicketPipelineStages] s ON s.[Id] = t.[Ticket status]
LEFT JOIN [YourConnection].[HubSpotV3].[Owners] o ON o.[Id] = t.[Ticket owner]
WHERE t.[Closed] = 0
LIMIT 25
```

### Recently created deals
```sql
SELECT [Id], [Deal Name], [Amount], [Create Date]
FROM [YourConnection].[HubSpotV3].[Deals]
WHERE [Create Date] >= DATEADD(month, -3, GETDATE())
ORDER BY [Create Date] DESC
LIMIT 50
```

### Members of a list
`ListMemberships` requires a `[ListId]` filter. **Do not add an `[ObjectTypeId]` predicate: it silently returns zero rows**, whether the query stands alone or joins to the object table. Read `[ObjectTypeId]` in the projection if you need it and filter client-side, or take the list's own object type from `Lists.[ObjectTypeId]`, where it is filterable.

Filtering on `[ListId]` alone works, including through a join, so either shape below is fine. The two-step is a little safer because an empty intermediate result is visible rather than collapsing into an empty final answer.

```sql
-- 1. find the list
SELECT [Id], [Name], [ProcessingType], [Size], [ObjectTypeId]
FROM [YourConnection].[HubSpotV3].[Lists]
```
```sql
-- 2. read its memberships (ListId only; ObjectTypeId is returned, never filtered on)
SELECT [ObjectId], [ObjectTypeId], [MembershipTimestamp]
FROM [YourConnection].[HubSpotV3].[ListMemberships]
WHERE [ListId] = <list-id>
```
```sql
-- 3. fetch those records
SELECT [Id], [Email], [First Name], [Last Name], [Lifecycle Stage]
FROM [YourConnection].[HubSpotV3].[Contacts]
WHERE [Id] IN (<object-id-1>, <object-id-2>)
```

### A company's deals, through associations (per-object shape)
```sql
SELECT DISTINCT d.[Id], d.[Deal Name], d.[Amount], d.[Deal Stage]
FROM [YourConnection].[HubSpotV3].[CompanyAssociations] a
INNER JOIN [YourConnection].[HubSpotV3].[Deals] d ON d.[Id] = a.[AssociationId]
WHERE a.[Type] = 'Deal' AND a.[Id] = <company-id>
```

### A company's deals, through associations (pairwise shape)
```sql
SELECT DISTINCT d.[Id], d.[Deal Name], d.[Amount]
FROM [YourConnection].[HubSpotV3].[CompaniesToDealsAssociations] a
INNER JOIN [YourConnection].[HubSpotV3].[Deals] d ON d.[Id] = a.[DealsId]
```

### What object types a record is associated with
```sql
SELECT [Type], COUNT(*) AS [Rows]
FROM [YourConnection].[HubSpotV3].[DealAssociations]
GROUP BY [Type]
```

### Super admins
```sql
SELECT [Id], [IsSuperAdmin], [PrimaryTeamId], [RoleId]
FROM [YourConnection].[HubSpotV3].[UserProvisioning]
WHERE [IsSuperAdmin] = 1
```

### A user's team name
```sql
SELECT u.[Id], u.[IsSuperAdmin], t.[Name] AS [Team]
FROM [YourConnection].[HubSpotV3].[UserProvisioning] u
LEFT JOIN [YourConnection].[HubSpotV3].[Teams] t ON t.[Id] = u.[PrimaryTeamId]
```

### Discovering custom property labels
```sql
SELECT [Name], [Label], [Type], [GroupName]
FROM [YourConnection].[HubSpotV3].[DealProperties]
WHERE [Label] LIKE '%score%'
```

### Custom object types defined in the portal
Project the columns you need — `CustomObjects` carries `[PropertiesAggregate]` and `[AssociationsAggregate]` columns large enough to overflow a response.
```sql
SELECT [Id], [Name], [FullyQualifiedName], [LabelPlural], [ObjectTypeId], [PrimaryDisplayProperty]
FROM [YourConnection].[HubSpotV3].[CustomObjects]
```

`[FullyQualifiedName]` takes the form `p<HubId>_<name>`, and `[ObjectTypeId]` takes the form `2-<id>`.

## Stored Procedures

- **CreateCustomObject** / **UpdateCustomObject** / **DeleteCustomObject** — define, modify, or remove a custom object type
- **CreateCustomProperty** / **UpdateCustomProperty** / **DeleteCustomProperty** — define, modify, or remove a property on an object
- **GetAccountDetails** — account type, time zone, currencies, data hosting location
- **DeleteContactPermanently** — GDPR permanent erasure of a contact and its associated content
- **UploadFile** / **DownloadFile** / **DeleteFile** — file manager operations

### Adding a custom property
```json
{
  "catalogName": "YourConnection",
  "schemaName": "HubSpotV3",
  "procedureName": "CreateCustomProperty",
  "parameters": {
    "@ObjectType": "deals",
    "@Name": "priority_score",
    "@Label": "Priority Score",
    "@Type": "number"
  }
}
```

### Permanent deletion is distinct from archiving
A `DELETE` archives a record recoverably. `DeleteContactPermanently` is irreversible GDPR erasure. Confirm with the user before calling it.

### File operations

**Uploading works through the base64 parameter.** `UploadFile` accepts `@EncodedFileData` (base64 content) together with `@FileName`, so it is usable directly:

```json
{
  "catalogName": "YourConnection",
  "schemaName": "HubSpotV3",
  "procedureName": "UploadFile",
  "parameters": {
    "@EncodedFileData": "<base64-encoded file content>",
    "@FileName": "report.txt",
    "@Access": "PRIVATE"
  }
}
```

The response returns the new `FileId`. `@Access` accepts `PUBLIC_INDEXABLE`, `PUBLIC_NOT_INDEXABLE`, or `PRIVATE`. Optional `@UploadFolderId` or `@UploadFolderPath` place the file in a folder; `@Overwrite` and the duplicate-validation parameters control collision behavior. The `@Content` parameter is a stream and cannot be supplied through a procedure call — use `@EncodedFileData`.

**To retrieve a file, query the `Files` table for its URL** rather than calling `DownloadFile`:

```sql
SELECT [Id], [Name], [Extension], [Size], [Url], [DefaultHostingUrl], [Access]
FROM [YourConnection].[HubSpotV3].[Files]
WHERE [Name] LIKE '%report%'
```

`[Url]` is a signed-URL redirect suitable for private files; `[DefaultHostingUrl]` is the direct hosted path.

**When the session provides dedicated file-transfer tools, prefer them for both directions.** They move the bytes out of band rather than through the conversation, so they handle content that base64 in a procedure call cannot. Follow each tool's own description for parameters and sequence. A completed upload must not be repeated. Any `FileLocation` / `FilePath` / `LocalPath` parameter refers to the CData cloud server's filesystem, not the user's machine.

## Write Operations

**`UPDATE` is the supported write path on the object tables**, subject to the connection's permissions. Target the record by `[Id]`:

```sql
UPDATE [YourConnection].[HubSpotV3].[Deals]
SET [Amount] = 12000, [Deal Stage] = 'qualifiedtobuy'
WHERE [Id] = <deal-id>
```

When writing a stage or owner, set the **id** value rather than the display label. Discover valid stage ids from `DealPipelineStages` and owner ids from `Owners`.

### Creating records

A raw `INSERT` against the object tables does **not** work. HubSpot assigns each record's primary key server-side and exposes `[Id]` as read-only, while the insert path requires a value for every non-nullable column that has no default and does not skip the read-only key — so the statement is rejected before the driver sees it.

**Creation is still supported**, through the connection's dedicated create tool for the object, which reaches the driver by a path that lets HubSpot generate the key. Use it in preference to any `INSERT`.

- **Never supply `[Id]`** on a create.
- An error naming the key column as *"neither nullable nor has a default value"* is a property of the insert path, not a missing column. Switch to the create tool rather than retrying variants or inventing a key value.
- **Confirm the create by reading the record back** by the id the tool returns.
- If no create tool is listed in this session, say plainly that creation is unavailable here, and offer to update an existing record or point the user to the HubSpot UI.

Creating *metadata* is unaffected: `CreateCustomObject` and `CreateCustomProperty` work through `executeProcedure` normally (see **Stored Procedures**).

### Write access control
A Connect AI connection may also be set to read-only. If an update or stored procedure is refused on permission grounds, direct the user to enable write access in their Connect AI connection settings. That is a different cause from the insert-path behavior above — do not send a user to connection settings over an insert error.

## V3-Specific Conventions

- **This surface carries the lookup tables the others lack.** `Owners`, `Teams`, `Roles`, `UserProvisioning`, `*PipelineStages`, `*Properties`, `Lists` / `ListMemberships`, and the custom-object metadata tables all exist only here. When a request needs owner names or portal-specific stage labels, this is the surface that can answer it.
- **Enum values are lowercase.** `[Lifecycle Stage]` is `lead` / `opportunity`, deal stages are `appointmentscheduled` / `qualifiedtobuy` / `closedwon`. Legacy uses TitleCase for the same concepts.
- **`ListMemberships` needs a `[ListId]` filter, and `[ObjectTypeId]` must not be filtered on.** A predicate on `[ObjectTypeId]` silently returns zero rows; `[ListId]` alone works, and works through a join. Project `[ObjectTypeId]` and filter client-side if you need to split by object type.
- **Project `CustomObjects` explicitly.** Its aggregate columns can overflow a response.
- **Metadata table prefixes are not reliably derivable.** `LineItemProperties` versus `Lineitems` versus `LineitemAssociations` all differ in capitalization. Confirm with a filtered `getTables` call.
- **`[Id]` is the primary key, not `[Record ID]`.** Both exist on object tables.
